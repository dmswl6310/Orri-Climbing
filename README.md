# 🧗 ORURI — 오르리

지역이나 현재 위치를 기준으로 클라이밍 암장을 탐색하는 Next.js App Router 프로젝트입니다.
기존 서비스 재구축 과정에서 검색 흐름, 서버·클라이언트 역할 분리, 접근성과 예외 처리를 개선하고 있습니다.

[서비스 데모](https://orri-climbing.vercel.app)

> 현재는 **기존 50개 목업 + 기능 체험용 가상 암장 3개**를 사용하는 체험 버전입니다.
> 사진·주소·운영 시간·평점·저장 수는 실제 영업 정보나 이용자 집계가 아닙니다.
> 실제 DB, 로그인, 개인 저장 기능은 아직 구현하지 않았습니다.

## 구현된 흐름

- 지역·암장 이름 검색 → 결과 정렬 → 상세 조회 → 다른 암장 탐색
- 일일권 예산·주차·샤워실·암벽화 대여·초보자 체험 강습을 함께 적용하는 조건 검색
- 적용한 조건 표시·개별 해제·필터 초기화·전체 초기화, 새로고침·뒤로 가기 복원
- 2~3개 암장 선택 → 가격·거리·운영 시간·시설·강습·난이도 비교 → 링크 공유
- 비교 후보는 탭의 sessionStorage에 유지하며 저장소 차단 시 메모리 선택으로 동작
- 검색어 자동완성: 방향키 선택, Enter 이동, Escape 닫기, 한글 조합 입력 보호
- 검색 조건을 URL에 유지하고 브라우저 뒤로 가기 시 입력값 복원
- 누적 저장 수 기준 인기순, 유효한 현재 좌표 기준 거리순 및 직선거리 표시
- GPS 거부·시간 초과 안내와 재시도, 이전 위치 응답이 새 검색을 덮어쓰지 않도록 취소 처리
- 검색 결과가 없을 때 별도의 추천 목록
- 이미지 누락·로딩 실패 대체 화면
- 로딩·오류 재시도·404 화면, 페이지별 제목
- 미확인 요금은 미등록으로 표시하며, 요금 데이터가 제공되면 암장별 표 렌더링

최신순은 기준 날짜 데이터가 없어 제공하지 않습니다. 로그인·마이페이지의 기존 주소는 검색으로 이동합니다.

## 실행

Node.js **24 LTS**와 npm을 기준으로 개발·CI를 검증합니다.

```bash
npm ci
cp .env.example .env.local
npm run dev
```

PowerShell에서는 복사 명령으로 `Copy-Item .env.example .env.local`을 사용합니다.
브라우저에서 [로컬 개발 서버](http://localhost:3000)를 엽니다.

`KAKAO_REST_API_KEY`는 카카오 Local API의 행정동 이름 변환에만 사용하는 **서버 전용 선택 변수**입니다.
키가 없어도 일반 검색과 GPS 거리 정렬은 사용할 수 있습니다.
GPS는 localhost 또는 HTTPS 환경에서 브라우저 위치 권한이 필요합니다.

## 기술 구성

| 영역 | 사용 기술 |
| --- | --- |
| UI / 라우팅 | Next.js 16, React 19, App Router |
| 언어 / 스타일 | TypeScript strict, Tailwind CSS 4, 로컬 Pretendard |
| 데이터 | 정적 목업 50개 + 가상 데모 3개, 선택적 Kakao Local API |
| 단위·컴포넌트 테스트 | Vitest, Testing Library, jsdom |
| 브라우저 테스트 | Playwright — 데스크톱·모바일 Chromium |
| 배포 / CI | Vercel, GitHub Actions |

정확한 설치 버전은 `package-lock.json`에 고정됩니다. Next.js와 관련 의존성은 보안 수정 버전으로 갱신했습니다.

## 데이터와 렌더링

```text
서버 페이지 (홈 / 검색 / 상세 / 비교)
  ├─ gymService → 정적 목업 데이터
  ├─ 검색 파라미터 검증 → 키워드·예산·시설 필터·인기/거리 정렬
  ├─ 비교 URL 검증 → 유효한 ID 최대 3개 조회
  └─ kakaoService → 좌표의 행정동 이름 (실패해도 목록 조회 가능)

클라이언트
  ├─ 검색 입력·자동완성 → URL 이동
  ├─ 위치 검색·정렬 → 이전 GPS 요청 무효화 → URL 이동
  ├─ 비교 선택 저장소 → SSR 격리·새로고침 복원·저장 실패 시 메모리 사용
  └─ GymImage → 지원하지 않는 URL·로딩 실패 시 대체 화면
```

- 홈은 1주일 재검증 설정을 사용합니다. 현재 목업 데이터 변경은 배포를 통해 반영됩니다.
- 검색·상세 페이지는 서버에서 데이터를 조회합니다.
- 자동완성은 전체 상세 데이터 대신 이름·지역·주소 요약을 전달받아 브라우저에서 필터링합니다.
- 검색 풀은 정적 배열이며 영구 DB 캐시가 아닙니다.
- 카카오 주소 응답에는 1시간 재검증과 3초 요청 제한을 적용합니다.
- 기존 50개 목업의 가격·초보자 강습을 임의로 채우지 않았습니다. `demo-1`~`demo-3`만 가상 예산·시설 데이터를 가지며 화면에도 가상 암장임을 표시합니다.
- 시설은 `true`(가능), `false`(불가), 누락(정보 없음)으로 구분합니다. 기존 시설 문자열은 명시적 별칭으로 해석하고, 명시한 boolean이 우선합니다.
- 예산 필터는 유효한 일일권 최저가를 사용합니다. 가격 0원도 유효하며 미등록 가격·시설은 해당 필터의 결과에서 제외합니다.
- 검색 결과 0개일 때 결과 수는 0개로 유지하고, 조건 밖 추천을 별도 영역으로 표시합니다.
- 비교 URL의 ID·순서가 표를 결정합니다. 공유 링크를 열어도 탭에 저장된 후보로 덮어쓰지 않습니다. 표에서 제거하는 동작과 후보 삭제는 구분됩니다.
- 거리 기준 좌표가 있는 비교 링크를 복사할 때는 좌표 포함 사실을 안내합니다. 자동 복사가 실패하면 직접 선택할 URL을 제공합니다.
- 거리 계산은 하버사인 공식의 직선거리이며, 이동 경로나 소요 시간이 아닙니다.

## 검증 명령

```bash
npm run lint
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

E2E 테스트가 3100 포트에서 프로덕션 서버를 실행합니다. 먼저 빌드해야 합니다.
Windows에서 설치된 Edge를 사용할 경우:

```powershell
$env:PLAYWRIGHT_CHANNEL = "msedge"
npm run test:e2e
```

- 서비스 테스트: 기본 정렬, 좌표 경계·반복 파라미터, 검색 없음, 외부 주소 API 실패
- 컴포넌트 테스트: 자동완성 키보드·한글 입력, 포커스, 이미지 실패·교체, 요금 누락
- 위치 테스트: 중복 클릭, 권한 거부, 재시도, 오래된 응답 무효화
- 브라우저 테스트: 검색·상세·뒤로 가기, 잘못된 URL, 위치 거부, 정렬 경합, 모바일 너비
- 조건·비교 테스트: AND 필터·미확인 데이터·초기화·URL 복원·GPS 조건 보존·최대 3개·저장 실패·비교 공유·표 내부 스크롤
- CI는 dev/main의 PR과 push에 위 검증을 실행합니다.
- 브라우저 테스트에서는 외부 사진 요청을 실패시켜 외부 서비스 상태와 무관하게 검증합니다.

## 주요 개선 기록

| 문제 | 수정 | 검증 |
| --- | --- | --- |
| 기본 인기순 표시와 실제 배열 순서 불일치 | 서버·UI가 같은 정규화 규칙 사용 | 인기순 첫 결과 및 잘못된 정렬 입력 테스트 |
| 좌표 0을 잘못 거부하거나 범위 밖 좌표 사용 | 유한 숫자·위경도 범위 검사 | 적도·본초자오선·잘못된 좌표 테스트 |
| 한글 조합 Enter가 검색을 제출 | 조합 이벤트 보호 | IME 이벤트 테스트 |
| 늦은 GPS 응답이 새 검색·정렬을 덮어씀 | 컨트롤 간 요청 취소와 응답 무효화 | 훅 및 브라우저 회귀 테스트 |
| 모든 암장에 동일한 요금·조회 수 표시 | 근거 없는 수치 제거, 선택 요금 모델 | 미등록·개별 요금 렌더링 테스트 |
| URL만 있으면 실패한 이미지가 남음 | 이미지 오류 상태 처리 | 실제 이미지 컴포넌트 오류 이벤트 테스트 |

## 후속 작업과 측정 원칙

1. Supabase 데이터 모델·마이그레이션 및 실제 암장 정보 검증
2. 인증·사용자별 저장·접근 권한·저장 실패 복구
3. 실제 데이터를 기준으로 캐시 갱신 정책 수립

성능 개선 수치와 Lighthouse 점수는 아직 측정 결과로 제시하지 않습니다.
자동완성 초기 로딩 전략은 최대 500개 규모를 가정한 선택이며, 현재 53개·500개 데이터에서 초기 전송량·입력 반응 시간·요청 수를 비교해 검증할 예정입니다.
이전 Page Router 서비스와의 비교에는 이전 저장소·기준 커밋과 동일 환경의 측정 결과가 필요합니다.
